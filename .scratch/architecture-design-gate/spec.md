# 架构设计门禁与中文架构阶段卡片

**Status:** ready-for-agent

## Problem Statement

开发任务视图当前从“规格与边界”直接进入“任务计划”，只能回答任务按什么顺序执行，不能回答系统应该怎样变化。系统架构关系与任务依赖关系因此容易混在一起；新项目也缺少一个明确、可批准的规划架构起点。直接把 Archify 查看器嵌进页面只能增加一张图，不能保证任务确实基于某个已批准架构版本拆分，也无法在架构变化后阻止新任务继续使用旧计划。

用户需要在任务拆分之前完成架构影响判断和架构设计，在开发过程中持续看到当前、目标与实际架构的关系，并让每张受影响工单绑定明确的架构修订和组件。开发任务视图仍然必须是只读投影，不能把“校验通过”“用户批准”“代码已实现”和“已经交付”混为同一状态。

## Solution

在正式规格与任务拆分之间增加“架构设计”门禁。存在组件、接口、数据流、信任边界、外部依赖或部署结构变化时，规划 Agent 使用 Archify 生成中文高层架构；新项目从“规划架构 v0”开始，已有项目没有图时先恢复并确认当前基线。Archify 的结构化 JSON 是架构事实源，交付 HTML 只负责展示，交付回执负责把两者的摘要和字节数绑定在一起。工具校验通过后仍需用户明确批准精确架构摘要，任务拆分才会解锁。

开发任务视图采用最终批准的 A 版“SDD 阶段卡片”：在“规格与边界”和“任务计划”之间增加可展开的“架构设计”卡片，卡片内呈现当前／目标／实际／差异生命周期、修订状态、中文 Archify 概览、受影响组件和关联工单。系统架构图与下方任务依赖 DAG 仍然分别建模，通过稳定组件 ID 和批准修订关联，不把系统关系当作执行依赖。

实施完成后生成实际架构，复核规划与实际差异，并在用户批准后将实际架构提升为长期项目基线。窄面板只提供架构概览和门禁状态，并提供“展开大图”入口；不会把无法阅读的小字冒充完整架构阅读体验。

## User Stories

1. As a Codex 用户, I want to 在任务拆分前看到独立的架构设计阶段, so that 我先确认系统应该怎样变化，再讨论开发顺序。
2. As a Codex 用户, I want to 让系统判断本次工作是否存在架构影响, so that 文案、样式和局部修复不会被不必要的架构流程拖慢。
3. As a Codex 用户, I want to 为跳过架构设计的工作记录明确理由, so that 跳过是可审计的决定而不是静默遗漏。
4. As a 新项目发起人, I want to 看到“当前架构不存在”是正常状态, so that 系统不会制造一张虚假现状图。
5. As a 新项目发起人, I want to 从需求规格生成规划架构 v0, so that 第一批任务有共同的结构依据。
6. As a 既有项目维护者, I want to 在项目没有架构文档时先恢复当前基线, so that 目标变化建立在真实现状上。
7. As a 既有项目维护者, I want to 人工确认恢复基线, so that 自动推断不会被当成无争议事实。
8. As a Codex 用户, I want to 第一张架构图只保留 5–12 个核心组件, so that 我能先理解系统边界而不是陷入代码细节。
9. As a Codex 用户, I want to 只在高风险路径需要时补充数据流或时序图, so that 架构设计保持与风险匹配。
10. As a Codex 用户, I want to 用全中文阅读组件、边界、连线、图例和说明, so that 我无需翻译即可评审设计。
11. As a 规划 Agent, I want to 把 Archify JSON 作为唯一架构事实源, so that 节点 ID、边界和连接可以稳定地供工单引用。
12. As a Codex 用户, I want to 把 Archify HTML 只当作展示工件, so that 页面不会从展示结果反推或篡改架构语义。
13. As a Codex 用户, I want to 看到交付回执中的源摘要、工件摘要和校验结果, so that 我知道图与事实源确实属于同一版本。
14. As a Codex 用户, I want to 明确批准精确架构版本摘要, so that “我看过并同意哪一版”不会含糊。
15. As a Codex 用户, I want to 让“校验通过”与“用户批准”保持两个状态, so that 工具不能替我做产品决定。
16. As a Codex 用户, I want to 在目标架构未批准前锁定任务拆分, so that 工单不会基于仍在变化的设计生成。
17. As a Codex 用户, I want to 在批准后解锁任务拆分, so that 工单可以引用同一份已批准架构。
18. As a 开发 Agent, I want to 在每张架构相关工单上读取批准修订, so that 我不会基于错误版本实施。
19. As a 开发 Agent, I want to 在工单上读取受影响组件 ID, so that 我能把任务目标定位到架构边界。
20. As a Codex 用户, I want to 让架构关系和任务依赖显示为两张独立图, so that 我不会把运行关系误解为实施顺序。
21. As a Codex 用户, I want to 从架构设计阶段卡片看到关联工单, so that 我能理解每个设计变化由哪些任务实现。
22. As a Codex 用户, I want to 从工单查看其影响的架构组件, so that 计划与系统结构保持可追溯。
23. As a Codex 用户, I want to 在架构事实源变化后立即看到旧批准过期, so that 新任务不会继续使用旧架构。
24. As a 正在实施的 Agent, I want to 在架构过期时完成当前安全检查点后暂停, so that 既不会中途破坏现场，也不会无限继续扩散旧设计。
25. As a Codex 用户, I want to 在过期状态中同时看到当前摘要和已批准摘要, so that 我能准确判断发生了什么变化。
26. As a Codex 用户, I want to 在流程视图始终看到架构门禁摘要, so that 切回任务 DAG 后不会漏掉架构风险。
27. As a Codex 用户, I want to 在展开的架构设计卡片中切换当前、目标、实际和差异, so that 不同生命周期事实不会混成一张图。
28. As a Codex 用户, I want to 在新项目默认打开目标架构, so that 空的当前基线不会被表现为错误。
29. As a Codex 用户, I want to 在架构过期或实际架构待复核时默认看到差异, so that 下一步行动清楚可见。
30. As a Codex 用户, I want to 在实施完成后生成实际架构, so that 规划图不会继续冒充代码事实。
31. As a Codex 用户, I want to 复核规划架构与实际架构的差异, so that 每项偏离都有解释并可决定是否接受。
32. As a Codex 用户, I want to 明确批准实际架构, so that 它可以安全提升为长期项目基线。
33. As a 后续任务发起人, I want to 复用最近一次批准的长期基线, so that 每次开发不必从零重建架构上下文。
34. As a Codex 用户, I want to 在架构文件缺失或回执不完整时看到不可验证状态, so that 页面不会展示伪可信门禁。
35. As a Codex 用户, I want to 在 HTML 摘要不匹配时阻止工件显示, so that 被修改的展示文件不会执行或误导我。
36. As a Codex 用户, I want to 在架构源已修改但上次 HTML 仍完整时看到上次交付图和明确警告, so that 我能参考最后一份可信图但不会误认它为当前设计。
37. As a Codex 用户, I want to 在右侧窄面板看到简洁架构概览, so that 门禁状态与任务上下文可以同时存在。
38. As a Codex 用户, I want to 用“展开大图”阅读完整节点, so that 390–526 像素宽度不会牺牲可读性。
39. As a 键盘用户, I want to 用键盘展开架构设计卡片并切换生命周期视图, so that 主要功能不依赖鼠标。
40. As a 色觉差异用户, I want to 通过文字、图标和边框共同识别状态, so that 状态不会只靠颜色表达。
41. As a 本地开发者, I want to 让架构工件只通过回环地址提供, so that 本地设计和路径不会暴露到网络。
42. As a 本地开发者, I want to 让 Archify 只在规划和更新阶段运行, so that 任务视图启动时不依赖 Archify、网络或额外服务。
43. As a Codex 用户, I want to 继续让 Markdown 规格、架构文件和工单成为事实来源, so that 任务视图保持只读且可检查。
44. As a Codex 用户, I want to 在架构或工单文件变化后看到页面自动刷新, so that 视图不会停留在旧状态。

## Implementation Decisions

- 架构门禁只适用于组件、接口、数据流、信任边界、外部依赖或部署结构变化。无架构影响的工作必须记录非空跳过理由，不能只省略架构目录。
- 架构生命周期固定为当前、目标、实际和长期基线。新项目没有当前基线时创建规划架构 v0；已有项目缺图时先生成并确认恢复基线。
- 第一张规划架构是 5–12 个核心组件的高层图。数据流、时序和更细视图按风险增加，不作为每个功能的固定负担。
- 每个功能的规划资产由四份独立事实组成：Archify JSON 架构源、交付 HTML、Archify 交付回执、流程决定／批准记录。批准记录只在用户明确批准后写入，并保存已批准的架构源摘要；页面本身没有批准按钮。
- 流程决定／批准记录使用版本化 JSON 契约，至少表达是否需要架构、模式是新项目还是既有项目、跳过理由以及已批准架构源摘要。生命周期状态由这些字段和文件校验结果推导，不另存一个容易漂移的状态字符串。
- Archify JSON 是架构语义和稳定组件 ID 的事实源。交付 HTML 只负责显示；任务视图不得从 HTML 解析组件、连接或批准状态。
- 交付回执必须同时匹配 JSON 与 HTML 的 SHA-256 和字节数。摘要和字节数使用 Node 标准库计算，不使用修改时间作为新鲜度依据。
- 工件状态至少区分：完整匹配、架构源已修改、HTML 被修改、缺少或不支持的回执。只有 HTML 摘要和字节数仍与回执一致时才允许返回展示工件；架构源变化时可以显示上次可信 HTML，但必须把批准标为过期并锁定新任务。
- 已批准摘要必须匹配回执中的架构源摘要，回执中的架构源摘要还必须匹配当前 JSON，任务计划才能解锁。工具校验成功不能自动写入批准记录。
- 每张架构相关工单增加 `architecture_revision` 和 `affects` 元数据。前者引用批准的架构源摘要，后者保存 Archify 稳定组件 ID；无架构影响工单不伪造这些字段。
- 架构关系和任务依赖分别建模。任务 DAG 继续只由 `depends_on` 决定；架构组件与工单只通过 `affects` 映射，不从组件连接推导执行顺序。
- 快照构建器仍是页面与 API 的唯一业务入口。它在现有规格和任务快照旁增加每个功能的架构决定、校验、生命周期、组件摘要和工单映射，不建立第二套服务端状态。
- 现有流程视图增加位于“规格与边界”和“任务计划”之间的“架构设计”阶段。它镜像门禁结果、下一步和锁定原因，不在同一张图里绘制系统拓扑。
- 采用批准的 A 版布局，不新增顶层模式切换。架构设计作为现有 SDD 卡片栈的第二张原生卡片，复用当前摘要、状态、折叠和键盘交互模式。
- 新项目正在初始化、架构必需且尚未批准、批准已过期或实际架构待复核时，架构设计卡片默认展开；门禁通过并进入任务执行后默认折叠，只保留批准摘要和状态。
- 展开的架构设计卡片依次呈现下一步、设计类型、架构变化、代码证据、生命周期选择、中文 Archify 概览、修订绑定、受影响组件和架构绑定工单。任务 DAG 继续位于独立的“依赖流程图”区域。
- 任务点击第一版只根据 `affects` 生成 Archify 稳定节点的焦点链接。父页面不与 iframe 建立双向消息协议，也不从 iframe 读取状态。
- Archify HTML 使用带 `allow-scripts` 且不带 `allow-same-origin` 的 sandbox iframe。工件响应阻止网络连接、对象、表单、剪贴板和全屏权限，并禁止把工件内容注入父页面 DOM。
- 窄面板中的 iframe 明确标为“架构概览”。完整节点阅读通过独立大图路由完成；第一版不承诺手机宽度下在内嵌画布完成精细阅读。
- 用户可见架构内容默认使用 `zh-CN`：组件、边界、连线、图例、状态和说明均为中文；Archify、Codex、JSON、SHA 等产品名或必要技术标识可以保留。
- 实施完成后由规划 Agent 生成实际架构并记录规划／实际差异。用户批准后，实际架构三件套与批准记录复制为项目级长期基线；任务视图只读取和投影，不主动移动或批准文件。
- Archify CLI 是规划阶段的可选外部工具，不成为任务视图运行时依赖。集成只使用 `validate` 和 `deliver` 公共命令，不导入 Archify 内部渲染模块。
- companion 工作流在正式规格完成后、任务拆分前执行架构影响判断和必要的架构批准；`to-tickets` 只为门禁通过或明确跳过的功能生成任务。原有“写完工单后打开任务视图、首次 implement 前保持可见”的步骤继续保留。
- 首发继续只支持本地 Markdown tracker 和回环 HTTP 服务，不修改 Matt Pocock 上游仓库，也不发布远端 PR。

## Testing Decisions

- 测试只验证用户可观察行为和公开快照／HTTP 契约，不锁定内部函数调用顺序、CSS 选择器细节或 Archify 内部实现。
- 最高层测试缝仍是“本地功能目录输入到任务图快照输出”。在现有规格与工单样例旁放置架构决定、JSON、HTML、回执和批准记录，断言门禁状态、下一步、组件映射和任务可执行性。
- 快照测试覆盖：无需架构且有跳过理由、新项目缺当前基线、既有项目恢复基线、待批准、已批准、架构源已修改、HTML 被修改、回执缺失或不支持、实际架构待复核和长期基线。
- 快照测试断言任务只有在批准摘要、当前架构源和回执完全一致时才可进入执行前沿；过期时未开始任务被锁定，进行中任务得到“安全检查点后暂停”的可见原因。
- 文件校验使用临时目录和 Node 标准库生成摘要与字节数。测试篡改 JSON 和 HTML 的不同分支，确保展示允许条件与任务门禁条件不是同一个布尔值。
- HTTP 集成测试从用户可访问路由验证：只有允许的功能内工件能返回；目录穿越、任意本地 HTML、摘要不匹配和缺少回执均被拒绝。
- HTTP 响应测试验证 sandbox iframe 所需的 CSP、Referrer-Policy、X-Content-Type-Options、Cross-Origin-Resource-Policy 和 Permissions-Policy；明确断言没有 `allow-same-origin`。
- 前端渲染测试验证 SDD 卡片栈出现五个阶段，架构设计位于规格与任务计划之间，系统架构图不会替换任务依赖 DAG。
- 前端渲染测试验证架构设计卡片包含中文生命周期、修订摘要、受影响组件、绑定工单、下一步和展开大图入口，并按初始化、待批准、已批准、过期和实际待复核状态正确展开或折叠。
- 使用真实 Archify 中文工件作为展示兼容样例，验证 `zh-CN` 图例、中文节点和焦点链接可以加载；不对生成 HTML 的内部字节布局做快照断言。
- 浏览器验收覆盖默认桌面宽度、526 像素和 390 像素。窄屏断言无横向溢出、状态与展开入口可用，但不把内嵌节点文字可读性列为通过条件。
- 无障碍验收覆盖键盘切换、可见焦点、iframe 标题、链接名称，以及状态同时具备文字／图标表达。
- 现有任务快照、SSE、规格视图、依赖 DAG、任务列表和回环地址测试必须继续通过，确保没有架构资产的旧功能得到兼容空态。

## Out of Scope

- 在开发任务视图中创建、拖拽、编辑或批准架构。
- 从代码自动推断一份可直接批准的正确架构，或自动判断所有架构偏差是否合理。
- 用架构连接自动生成任务依赖，或把系统拓扑与任务 DAG 合并成一张图。
- iframe 与父页面之间的 `postMessage` 双向同步、内嵌编辑器或自定义 Archify 渲染器。
- 在 390–526 像素窄面板内保证每个复杂架构节点都可完成精细阅读。
- 私有 GitHub evidence、dirty working tree 证明、提交级代码新鲜度或自动 Git 操作。
- GitHub、GitLab、Linear、Jira 等远程 tracker adapter。
- 修改或发布 Matt Pocock 上游技能、创建 PR、提交、推送或安装新的依赖。
- 自动提交长期基线、自动关闭工单、自动部署或将本地校验冒充远端发布证明。

## Further Notes

- 最终批准的中文 A 版原型是本规格的交互主来源；原型中的 B、C 只用于比较，不进入正式实现。
- 原型已证明 Archify `zh-CN` 工件可在无 `allow-same-origin` 的 sandbox iframe 中运行，并通过 showcase 级 9/9 校验。
- 架构批准修订是产品决定；交付回执是工具证据；实际架构是实施后的事实。三者必须在界面和数据模型中保持不同名称。
- 第一版优先复用现有快照、原生 HTTP、HTML/CSS/JavaScript 和 Node 测试，不引入数据库、前端框架、图形库或第二个常驻进程。
